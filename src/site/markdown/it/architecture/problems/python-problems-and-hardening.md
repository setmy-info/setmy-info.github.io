# Hardening Python Against Automatic Code Execution and Supply Chain Attacks

## Problem Statement

Modern Python applications depend heavily on third-party packages from repositories such as PyPI. While this ecosystem
enables rapid development, it also introduces supply chain risks. A compromised package, compromised maintainer account,
or malicious dependency update can execute arbitrary code on a developer's workstation, CI/CD pipeline, or production
system.

One particularly dangerous Python feature is the automatic processing of .pth files during interpreter startup.

When Python starts, it normally imports the site module. As part of this initialization, the interpreter scans the
site-packages directories for .pth files. Although these files were originally intended to extend sys.path, they may
also contain executable import statements.

For example:

import malicious_payload

This code executes automatically during interpreter startup, before the application's own code begins running.

As demonstrated by the LiteLLM supply chain incident, this means that simply installing a compromised package may be
sufficient for malicious code to execute. The application does not need to explicitly import the compromised package.

This significantly increases the attack surface because arbitrary code may execute whenever Python starts, including
when running:

- Python REPL
- pytest
- pip
- IPython
- Build scripts
- Development tools
- CI/CD pipelines
- Production services

Automatic startup execution should therefore be considered a high-risk capability in environments with strict security
requirements.

---

# Security Recommendations

The following defense-in-depth strategy significantly reduces the risk of supply chain attacks and unintended code
execution.

## 1. Disable Automatic site Initialization Where Possible

If your application architecture allows it, start Python with:

python -S

Benefits:

- Prevents importing the site module.
- Prevents automatic processing of .pth files.
- Prevents execution of sitecustomize.py.
- Prevents execution of usercustomize.py.

This directly mitigates attacks relying on automatic interpreter startup execution.

---

## 2. Use Isolated Virtual Environments

Never share Python environments between unrelated projects.

Recommendations:

- One virtual environment per project.
- Rebuild environments from scratch instead of reusing old ones.
- Avoid installing unnecessary packages.

Isolation reduces the impact of a compromised dependency.

---

## 3. Pin Every Dependency

Avoid floating versions such as:

package>=1.0

Instead use exact versions:

package==1.2.3

Even better, use lock files generated by tools such as:

- uv
- Poetry
- Pipenv

This prevents unexpected upgrades to malicious releases.

---

## 4. Verify Package Integrity

Whenever possible:

- Use package hashes.
- Require hash verification during installation.
- Verify downloaded artifacts.

Example:

pip install --require-hashes

Hash verification prevents unnoticed package replacement.

---

## 5. Scan Dependencies

Regularly audit dependencies using Software Composition Analysis (SCA) tools such as:

- pip-audit
- Safety
- OSV Scanner
- Dependabot
- Renovate

These tools help detect known vulnerable or compromised packages.

---

## 6. Inspect Automatically Executed Files

Include automated CI/CD checks for suspicious files such as:

- .pth
- sitecustomize.py
- usercustomize.py

Unexpected additions should trigger manual review.

---

## 7. Run Applications with Least Privilege

Never execute production services as root.

Instead:

- Use dedicated service accounts.
- Remove unnecessary Linux capabilities.
- Use read-only filesystems whenever possible.

Compromised code should have minimal privileges.

---

## 8. Use Containers for Isolation

Containerization limits the blast radius of a compromised dependency.

Recommended practices:

- Minimal base images
- Read-only filesystem
- Non-root user
- Restricted networking
- Limited mounted secrets

---

## 9. Restrict Outbound Network Access

Many supply chain attacks attempt to:

- Download additional payloads
- Exfiltrate credentials
- Contact command-and-control servers

Restrict outbound connections to only approved destinations.

---

## 10. Protect Secrets

Avoid exposing credentials through environment variables whenever possible.

Use dedicated secret management solutions, for example:

- HashiCorp Vault
- AWS Secrets Manager
- Azure Key Vault
- Kubernetes Secrets (with proper encryption)

Compromised code should never gain unrestricted access to sensitive credentials.

---

## 11. Harden CI/CD Pipelines

CI environments often have elevated permissions.

Recommendations:

- Use ephemeral runners.
- Grant minimum required permissions.
- Avoid long-lived tokens.
- Rotate credentials regularly.
- Verify build artifacts.

---

## 12. Prefer Trusted Package Publishing

When publishing Python packages:

- Require Multi-Factor Authentication (MFA).
- Use hardware security keys (FIDO2/WebAuthn).
- Prefer Trusted Publishing (OIDC).
- Sign releases when possible.

These measures reduce the likelihood of compromised package releases.

---

# Additional Considerations

Even with all recommended protections, no single control completely eliminates supply chain risk.

For example:

- python -S prevents automatic execution through .pth files.
- It does not prevent execution of malicious code when an application explicitly imports a compromised package.

Therefore, security should rely on multiple independent layers rather than any single mitigation.

---

# Recommended Baseline for High-Security Python Services

A practical baseline configuration includes:

- Start Python with python -S whenever feasible.
- Use isolated virtual environments.
- Pin all dependencies.
- Verify package hashes.
- Continuously audit dependencies.
- Automatically detect unexpected startup files (.pth, sitecustomize.py, usercustomize.py).
- Run as a non-root user.
- Use containers with read-only filesystems.
- Restrict outbound network access.
- Store secrets in a dedicated secret manager.
- Harden CI/CD pipelines.
- Use trusted package publishing and strong maintainer authentication.

This defense-in-depth approach significantly reduces the attack surface associated with Python supply chain attacks
while remaining practical for modern production environments.
